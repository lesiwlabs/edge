Use lesiw.io/tools to automatically fix and report on issues.

Begin by formatting the code.

    go run lesiw.io/tools/cmd/fmt@latest ./...

Then automatically apply fixes.

    go run lesiw.io/tools/cmd/fix@latest ./...

Report on what's left.

    go run lesiw.io/tools/cmd/vet@latest ./...

Systematically work through all vet failures until vet passes.

If long lines are reported, use that as a signal to restructure, not merely
rewrite. The linelen analyzer is there to force you to reconsider whether a
line is doing too much, is too complex, or is merely too hard to read.

linelen does not require all lines to be under 80 columns. Some are exempt:
function definitions, lines containing URLs, and lines that are dominated by a
string (to maintain error, log, and message grepability).

Line breaks should carry semantic meaning. Bin-packing is the neutral state.

    // A call in which no arguments are singled out,
    // the arguments cannot fit in one line (forcing wrapping),
    // and the lines are kept relatively even.
    f(
        "foo", "bar", "biz", "baz", "zip", "qux", "quux", "corge",
        "garply", "waldo", "fred", "plugh", "xyzzy", "thud",
    )

    // A Go context being held separately from other arguments.
    funcContext(ctx,
        "https://example.com", map[string]string{"User-Agent": "Go net/http"},
    )

    // A fsys from the io/fs package, where fsys is a stand-in for a receiver.
    fs.Stat(fsys,
        "/some/very/long/path/that/prevents/this/call/from/being/one/line",
    )

    // A command where the code highlights the package list.
    cmd := exec.Command("apt-get", "install", "-y",
        "pkg1",
        "pkg2",
    )

Treat vet as the source of truth. Do not attempt to mechanical fixes or create
ad-hoc scripts to measure line lengths. If something could be mechanically
fixed, it would already be part of the fix suite; assume that all remaining
reports require manual judgement by default.

As you apply corrections, return to the beginning of this procedure. For
example, after making manual fixes on vet findings, return to the format step,
followed by the auto-fix step, followed only then by another vet. This is to
reduce churn (for example, manually fixing things that would be mechanically
fixed by another fmt or fix run).

Once you have passed the vet step, spin off a reviewer with no shared context.
If you are an agent operating in a harness, create a subagent and prompt it
with https://lesiw.io/review.txt. If no subagent capability exists,
https://lesiw.io/subagent.txt describes how to create an ad-hoc one with tmux
and pi, and how to wait for it without guessing at timings.

If there are review findings, address them, and return to the beginning of the
procedure - fmt, fix, vet, review. Continue until there are no more remaining
findings from vet or the reviewer.
